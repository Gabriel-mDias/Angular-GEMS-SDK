# Migração `1.1.0` → `2.0.0`

Guia de upgrade da `@gabriel-mdias/angular-gems-sdk`. Para a migração de um projeto legado sem SDK,
veja [`MIGRATION.md`](../../MIGRATION.md); este documento cobre apenas quem já está na `1.1.0`.

> **A faixa 1.x está encerrada, sem manutenção.** Não haverá correções, nem de segurança, para a
> 1.1.0 ou anterior. Não há caminho de suporte que não passe por esta migração.

---

## Por que a versão é MAJOR

Duas razões independentes. Cada uma sozinha já exigiria o salto.

### 1. Salto de plataforma

Os `peerDependencies` passam a exigir `@angular/* ^22.0.0`. Um projeto em Angular 20 ou 21 **não
instala** esta versão. TypeScript sobe para 6.0 e `ng-packagr` para 22.

### 2. Dois caminhos fail-open foram fechados na autorização

Rota ou elemento que hoje aparece por causa de um desses caminhos passa a ser negado. É o efeito
pretendido, não um dano colateral — mas é uma mudança de comportamento observável, e por isso está
nomeada aqui em vez de escondida numa lista de correções.

---

## Passo a passo

### 1. Suba a plataforma do seu projeto para o Angular 22

A SDK não instala em Angular 20 ou 21. Rode primeiro os schematics do Angular no **seu** projeto,
até ele estar verde em 22, e só então troque a versão da SDK.

```bash
ng update @angular/core@22 @angular/cli@22
```

### 2. Instale a 2.0.0 — e tire o `--legacy-peer-deps`

```bash
npm install @gabriel-mdias/angular-gems-sdk@^2.0.0
```

A flag deixou de ser necessária **por causa desta SDK**: os peers de Angular do `keycloak-angular`
16 são relaxados por `overrides` dentro do pacote. Se a instalação do seu projeto ainda exigir a
flag, a causa é outra dependência sua — vale investigar em vez de reintroduzir a flag por hábito.

### 3. Revise cada uso de `gemsRoleGuard` e `gemsHasRequiredRoles`

**Este é o passo que pode mudar o que o seu usuário vê.** Faça-o com atenção.

#### 3.1. O guard sem Keycloak agora nega

```ts
// 1.1.0: sem KeycloakService disponível, o guard LIBERAVA
// 2.0.0: sem KeycloakService disponível, o guard NEGA
```

A mesma condição cobria dois casos muito diferentes: "esta aplicação não usa autenticação" e "esta
aplicação usa autenticação, e a injeção do serviço falhou". Liberar atendia ao primeiro à custa do
segundo — e o segundo é uma falha de configuração servindo rota protegida a qualquer um.

**Não há opção de compatibilidade, e isso é deliberado.** Aplicação que de fato não usa autenticação
não põe `gemsRoleGuard` na rota. Se o seu projeto o usa numa rota que deve ser aberta, remova o
guard dela.

Confirme que `provideGemsKeycloak` está de fato no seu `ApplicationConfig`. Se ele estiver, nada
muda para você.

#### 3.2. Lista de papéis vazia agora nega

```ts
// ERRADO — e na 1.1.0 isto liberava a rota para todo mundo, em silêncio
{ path: 'admin', component: AdminComponent, canActivate: [gemsRoleGuard],
  data: { role: ['ADMIN'] } }        // ← singular

// CERTO
{ path: 'admin', component: AdminComponent, canActivate: [gemsRoleGuard],
  data: { roles: ['ADMIN'] } }       // ← plural
```

Procure no seu projeto por `data: { role:` no singular, e por `[gemsHasRole]` vinculado a um array
que possa chegar vazio:

```bash
grep -rn "data: { role:" src/
grep -rn "gemsHasRole" src/
```

Na 1.1.0, uma lista ausente ou vazia liberava. Na 2.0.0 ela nega. Elemento que deve ser visível para
qualquer um simplesmente **não usa** essas funções — não passe uma lista vazia esperando que libere.

### 4. Espere ver mensagens de erro que antes não apareciam

`gems-field-error` estava quebrado na 1.1.0: o `computed()` só reavaliava quando `control()` mudava
— uma vez, na vinculação, com o campo ainda intocado — e memorizava `''` para sempre. O componente
existia, ocupava espaço no template e nunca exibia nada.

Na 2.0.0 ele funciona. Se o seu layout foi ajustado assumindo que o espaço da mensagem ficava
sempre vazio, ele vai passar a ser ocupado.

### 5. `gems-input-password` ganhou política de senha — e ela vem **ligada**

```html
<gems-input-password
  [enforcePolicy]="true"      <!-- padrão: true -->
  [showCriteria]="true"       <!-- padrão: true -->
  [username]="usuario"
  [email]="email"
  [matchControl]="form.controls.confirmacao" />
```

A política exige 12 caracteres (`GEMS_PASSWORD_MINIMUM_LENGTH`), minúscula, maiúscula, caractere
especial (`GEMS_PASSWORD_SPECIAL_CHARACTER_PATTERN`) e ausência de espaço em branco; e recusa senha
que coincida com o `username` ou o `email` informados. `matchControl` produz `passwordMismatch`.

**Se você já tinha a sua própria política** aplicada por fora do componente, e não quer a da SDK,
desligue-a explicitamente:

```html
<gems-input-password [enforcePolicy]="false" [showCriteria]="false" />
```

Tipos e constantes novos, exportados de `/components`: `GemsPasswordPolicyErrors`,
`GemsPasswordIdentityErrors`, `GemsPasswordCriterion`, `GEMS_PASSWORD_MINIMUM_LENGTH`,
`GEMS_PASSWORD_SPECIAL_CHARACTER_PATTERN`.

### 6. Se você contribui com a SDK: os testes agora são Vitest

Karma, Jasmine e `@types/jasmine` saíram; o construtor é `@angular/build:unit-test`. `npm ci`
depende do `package-lock.json`, que passou a ser versionado.

> **Armadilha que custou caro aqui, e vale para qualquer projeto Angular:** a opção `include` do
> construtor de teste é relativa ao **`sourceRoot`**, não à raiz do projeto. Os specs do entry point
> `auth`, que fica fora do `sourceRoot`, rodavam como zero arquivos — e a suíte reportava verde.
> Se você tem entry point secundário com testes, confira que eles estão de fato sendo executados,
> pela **contagem de arquivos**, não pela cor da saída.

## Checklist

- [ ] Projeto em Angular 22, verde, **antes** de trocar a versão da SDK
- [ ] `npm install @gabriel-mdias/angular-gems-sdk@^2.0.0` sem `--legacy-peer-deps`
- [ ] Nenhuma ocorrência de `data: { role:` no singular
- [ ] Nenhum uso de `gemsRoleGuard` numa rota que deve ser aberta
- [ ] `provideGemsKeycloak` presente no `ApplicationConfig`
- [ ] Rotas protegidas testadas **logado e deslogado** — as duas, não só a primeira
- [ ] Layout revisado onde `gems-field-error` passou a exibir mensagem
- [ ] Decisão tomada sobre `enforcePolicy` em cada `gems-input-password`
